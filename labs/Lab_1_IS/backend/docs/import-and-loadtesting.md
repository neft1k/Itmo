# Массовый импорт, история операций и нагрузочное тестирование

## Импорт транспортных средств

- Эндпоинт: `POST /api/vehicles/import`
- Формат: `multipart/form-data` c полем `file`, содержащее JSON-массив объектов в кодировке UTF-8.
- Структура элемента массива:  
  ```json
  {
    "name": "import-a",
    "coordinates": { "x": 500.5, "y": 50 },
    "type": "CAR",
    "enginePower": 150,
    "numberOfWheels": 4,
    "capacity": 55.0,
    "distanceTravelled": 33.0,
    "fuelConsumption": 9,
    "fuelType": "MANPOWER"
  }
  ```
- Координаты задаются внутри вложенного объекта `coordinates` той же записи.
- Допустимые значения `type`: `CAR`, `SHIP`, `HOVERBOARD`; `fuelType`: `MANPOWER`, `PLASMA`, `ANTIMATTER` или `null`.
- Заголовки авторизации: `X-User` (любая строка, например `user42`) и `X-Role` (`user` или `admin`). Их достаточно переключать на фронтенде через кнопку admin/user.
- Обработка выполняется в одной транзакции уровня `SERIALIZABLE`. При любой ошибке ни один объект не попадает в БД, а в истории появляется запись со статусом `FAILED`.
- Ответ при успехе (`201 Created`): JSON с информацией об операции импорта.
- Ошибки в формате или нарушении ограничений возвращаются с кодом `400`. Нарушение уникальности — `409`.

## История операций импорта

- Эндпоинт: `GET /api/vehicles/import/history` — список операций. Обычный пользователь видит только свои, администратор — все.
- Эндпоинт: `GET /api/vehicles/import/{id}` — подробности конкретного импорта (с проверкой прав).
- Статусы: `IN_PROGRESS`, `SUCCESS`, `FAILED`. Для успешных операций указывается число созданных объектов.

## Ограничения уникальности

- Имя транспортного средства (`Vehicle.name`) уникально без учета регистра.
- Координаты (`coordinates.x`, `coordinates.y`) уникальны и не могут повторяться у разных транспортных средств.
- Контроль выполняется на уровне бизнес-логики; БД ограничений не содержит. При нарушении возвращается `409 Conflict` с сообщением об ошибке.

## Изменение уровней изоляции транзакций

- Для операций создания/обновления (`VehicleRepository.save`) и пакетного импорта (`VehicleImportService`) уровень изоляции установлен в `SERIALIZABLE`.
- В ходе сценария Apache JMeter выявлено, что при `READ COMMITTED` параллельные пользователи могли создать объекты с одинаковыми именами до коммита второй транзакции. Переход на `SERIALIZABLE` гарантирует ошибку повторной сериализации и предотвращает появление дубликатов.
- Удаление и чтение остаются на стандартном уровне, т.к. конфликтов при параллельном удалении не зафиксировано.

## JMeter-сценарий

- Файл: `backend/jmeter/vehicle-scenario.jmx`
- Пример запуска:  
  ```bash
  jmeter -n -t backend/jmeter/vehicle-scenario.jmx -l backend/jmeter/results.jtl
  ```
- Сценарий включает:
  1. Инициализацию общей сущности и общих значений (`Setup Thread Group`).
  2. Одновременные попытки нескольких пользователей создать объект с одинаковым именем.
  3. Параллельный апдейт и удаление одного и того же объекта двумя администраторами.
  4. Параллельные операции импорта (администратор и пользователь) с последующей проверкой истории.
- Для импорта используется JSON `backend/jmeter/import-sample.json`. При необходимости его можно скорректировать (важно сохранять уникальные значения).
